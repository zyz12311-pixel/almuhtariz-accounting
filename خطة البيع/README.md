# خطة البيع والتوزيع التجاري — المحترز للمحاسبة

## القرار المقترح
تأجيل تطوير نظام بيع البرنامج والاشتراكات إلى ما بعد استكمال التوثيق الضريبي، مع مراعاة استقلال المنشآت ووحدات الإصدار من الآن. هذه وثيقة تخطيط وليست إعلان جاهزية أو اعتماد.

## الوضع المرجعي
- توجد قاعدة SQLite محلية قابلة للتهيئة المستقلة، وإعداد أول للمنشأة والمالك، ومسار بيانات قابل للتخصيص.
- توجد تراخيص موقعة Ed25519 مرتبطة بالرقم الضريبي، وحدود المستخدمين ونقاط البيع، وتاريخ انتهاء ووضع قراءة فقط عند الانتهاء أو عدم المطابقة.
- توجد أداة إصدار تراخيص للمطور، وأساس لمزامنة الفروع وعزل المنشآت في Supabase؛ لا يُعد ذلك إثباتًا لاكتمال الخدمة السحابية.
- التشغيل الحالي على Windows يعتمد على Node.js وملف start-windows.cmd؛ لا يوجد مثبت مستقل مثبت الجاهزية في الفحص السابق.

## متطلبات لا تؤجل أثناء التوثيق
- استقلال بيانات كل منشأة ورقمها الضريبي وهوية التثبيت.
- استقلال مفاتيح وشهادات ZATCA وسلسلة ICV وPIH لكل وحدة إصدار فعلية.
- فصل ملفات البرنامج عن البيانات والتراخيص والشهادات؛ عدم تضمين أسرار أو قاعدة عميل في حزمة التوزيع.
- عدم تعطيل الإبلاغ عن الفواتير المعلقة أو الوصول إلى الأرشيف والتصدير بسبب انتهاء الترخيص التجاري.
- حماية حالة الإصدار عند التحديث والاستعادة ومنع تكرار العداد أو المستندات.
- إعادة اختبارات الامتثال بعد التغليف النهائي.

## المرحلة الأولى بعد التوثيق: الحماية التجارية
- منع العودة إلى تجربة غير محدودة بحذف الترخيص؛ تحديد مدة التجربة.
- تشديد مطابقة الرقم الضريبي وهوية التثبيت، مع مسار مشروع لنقل الترخيص عند استبدال الجهاز.
- معالجة التلاعب بالوقت، وتجديد وإلغاء التراخيص، وسياسة العمل دون إنترنت.
- التحقق من تطبيق حدود المستخدمين ونقاط البيع والوحدات على الخادم، لا الواجهة فقط.
- إبقاء مفتاح توقيع التراخيص الخاص لدى المطور خارج المستودع وحزم العملاء.
- اختبار الترخيص الصحيح والمنتهي والتالف وغير المطابق والحذف والنسخ والتجديد.

## المرحلة الثانية: لوحة إدارة البيع
لوحة مستقلة للمطور لإدارة العملاء والمنشآت والتثبيتات والتراخيص والباقات والاشتراكات والتجديد والإلغاء وسجل العمليات. لا تجمع بيانات محاسبية أو مفاتيح ZATCA الخاصة بالعملاء دون ضرورة وتفويض.
الباقات المقترحة (غير معتمدة): أساسية 2 مستخدم/1 نقطة بيع؛ متقدمة 5/3؛ احترافية 20/10. الأسعار والمدد وسياسة الدفع تحدد لاحقًا.

## المرحلة الثالثة: مثبت Windows والتحديثات
- مثبت مستقل EXE أو MSI لنظام Windows 10/11 ‏64-bit، مع بيئة Node.js المتوافقة.
- تشغيل الخادم المحلي وفتح الواجهة وإنشاء اختصار ومعالج إعداد أول للمنشأة والمالك والترخيص.
- تخزين البيانات في مسار دائم مناسب للصلاحيات، مستقل عن ملفات البرنامج.
- تحديثات موقعة والتحقق من سلامتها، ونسخ احتياطي قبل الترحيل، ومسار استعادة آمن.
- عدم حذف بيانات العميل عند إعادة التثبيت أو التحديث؛ تحديد سياسة إزالة البرنامج بوضوح.
- اختبار الشبكة المحلية وTLS والطابعات والباركود وإعادة التشغيل.

## المرحلة الرابعة: قبول التوزيع
- تثبيت نسختين نظيفتين لمنشأتين مختلفتين، والتأكد من عدم اختلاط البيانات والتراخيص والهويات والشهادات.
- اختبار عدة مستخدمين ونقاط بيع داخل المنشأة، والنسخ الاحتياطي والاستعادة والترقية.
- اختبار استمرار الإبلاغ النظامي عند انتهاء الاشتراك، وتجديد الترخيص دون تغيير هوية الإصدار.
- اختبار Windows 10/11 فعليًا وإعادة اختبارات المحاسبة والمخزون والتسعير والترميز وZATCA بعد التغليف.
- لا يعتمد الإطلاق على CI وحده؛ يلزم قبول ميداني موثق.

## المرحلة الخامسة: الإطلاق والتوسع
توزيع محلي مستقل أولًا. يؤجل نموذج SaaS والمزامنة المركزية إلى حين إثبات عزل المنشآت والمصادقة والمزامنة واستعادة البيانات تشغيليًا. تجهيز الدعم والتحديثات وسياسات الخصوصية والنسخ الاحتياطي قبل البيع.

## ضوابط التنفيذ
القطاع التجاري فقط؛ لا تفعيل للقطاع الهندسي أو الحفلات. المحافظة على الوظائف المحاسبية والمراحل الأربع المنجزة. الاختبارات على قواعد معزولة، ولا تعديل لقاعدة العميل الأصلية دون تفويض. لا إصدار فواتير حقيقية لأغراض الاختبار. لا يبدأ تنفيذ هذه الخطة بمجرد إيداعها.
